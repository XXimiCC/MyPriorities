# Worker

Бэкенд приложения: вход через Telegram, хранение данных в D1, ночной отчёт о
занятом месте. Живёт отдельным пакетом по той же причине, что `docs/` и
`tools/shots/`: wrangler тянет workerd на ~80 МБ, и в корневом `package.json`
это добавилось бы к каждой сборке приложения на Vercel.

## Локально

Всё работает без аккаунта Cloudflare — `wrangler dev --local` поднимает workerd
и SQLite прямо на машине.

```sh
npm install                 # в этом каталоге
cp .dev.vars.example .dev.vars   # и подставить свои значения
npm run db:local            # создать таблицы в локальной D1
npm run dev                 # http://127.0.0.1:8799
```

Приложению адрес передаётся через `VITE_SYNC_URL` — см. `.env.example` в корне.
Порт приложения должен быть в `ALLOWED_ORIGINS` (см. `wrangler.toml`), иначе
браузер не выпустит запрос.

## Развёртывание

```sh
npx wrangler login
npx wrangler d1 create mypri        # id из вывода — в wrangler.toml
npx wrangler kv namespace create SHOTS  # id из вывода — тоже в wrangler.toml
npm run db:remote                   # применить миграции на проде

npx wrangler secret put TELEGRAM_BOT_TOKEN
npx wrangler secret put JWT_SECRET     # node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"
npx wrangler secret put REPORT_CHAT_ID # куда слать ночной отчёт, см. ниже
npx wrangler secret put DEVKIT_TOKEN   # ключ командной строки для тикетов

npm run deploy
```

`db:remote` и `db:local` применяют **всю** папку `migrations/`, а не один файл:
добавленная миграция подхватывается сама, и забыть её нельзя.

**Порядок при выкатке важен: сначала миграция, потом `deploy`.** Новый код
обращается к колонкам, которых в старой схеме ещё нет, и между двумя командами
сервер отвечает 500 на всё, что их трогает.

Если `db:remote` обрывается с `Assertion failed` вместо вопроса про
подтверждение — это wrangler не смог показать диалог в неинтерактивной оболочке.
Тогда:

```sh
CI=true npm run db:remote   # подтверждение пропускается, миграция применяется
```

Кому можно заводить тикеты из [панели отладки](../docs/dev/devkit.md), задаётся
в `wrangler.toml` переменной `DEVKIT_ALLOW` — номера Telegram через запятую.
Пусто — нельзя никому.

## Куда слать отчёт

```sh
npm run chat-id
# или, если в .dev.vars лежит тестовый токен:
TELEGRAM_BOT_TOKEN=<настоящий> npm run chat-id
```

Идентификатор чата нельзя вывести ни из ссылки-приглашения, ни из имени: его
знает только Telegram и отдаёт лишь вместе с настоящим сообщением. Поэтому
сначала надо боту написать — в личку или в группу, — и только потом спрашивать.

В группе есть тонкость: у ботов по умолчанию включён режим приватности, обычных
сообщений они не видят. Писать надо команду, например `/start`. Идентификатор
группы отрицательный, у супергрупп начинается с `-100`.

После развёртывания: адрес Worker — в `VITE_SYNC_URL` приложения, домен
приложения — в `ALLOWED_ORIGINS`.

Секреты в файлах не живут. `.dev.vars` нужен только локально и в `.gitignore`.

## Сколько дней до первой записи

`profiles.first_op_at` — момент первой операции человека, рядом с `created_at`,
моментом появления профиля. Разница между ними и есть ответ на вопрос «сколько
дней от входа до первой ценности». Отдельно этот признак записан потому, что
свёртка журнала стирает его безвозвратно: см. `migrations/0004_first_op.sql`.

Читается запросом, разово — в отчёт он не попадает намеренно, ночная сводка
следит за местом в базе, а не за когортами:

```sh
npx wrangler d1 execute mypri --remote --command \
  "select cast(julianday(first_op_at) - julianday(created_at) as integer) as days,
          count(*) as people
     from profiles
    where first_op_at is not null
    group by days order by days"
```

`first_op_at is null` — либо человек ещё ни разу ничего не записал, либо его
журнал свернулся до того, как появилась эта колонка. Сколько таких:

```sh
npx wrangler d1 execute mypri --remote --command \
  "select count(*) as people from profiles where first_op_at is null"
```

## Что внутри

| Файл | О чём |
|---|---|
| `migrations/0001_init.sql` | Схема: профили, устройства, сессии, документы, журнал операций, свёртки |
| `migrations/0002_tickets.sql` | Тикеты из встроенной панели отладки |
| `migrations/0003_ticket_queue.sql` | Состояние «взято в работу» у тикетов |
| `migrations/0004_first_op.sql` | Момент первой записи в профиле |
| `src/telegram.ts` | Проверка подписи `initData`, сообщения и картинки от бота |
| `src/jwt.ts` | Свои токены на HS256 |
| `src/auth.ts` | Вход, продление, выход |
| `src/devkit.ts` | Тикеты: приём, выдача командной строке, закрытие, уборка |
| `src/report.ts` | Ночной отчёт о занятом месте |
| `src/index.ts` | Маршруты |

У `/devkit/*` две двери, и это не недосмотр: приложение приходит с обычным
токеном сессии (общий ключ попал бы в бандл и перестал быть ключом), а
командная строка — с `DEVKIT_TOKEN` в своём заголовке (`initData` ей взять
неоткуда: подпись выдаёт клиент Telegram, а не терминал).

## Решения, которые стоит помнить

**Подпись проверяется по HMAC, а не по Ed25519.** У Telegram с Bot API 8.0 есть
второй путь — подпись, которую можно проверить без токена бота. Он тут не нужен:
токен у Worker и так есть, а захардкоженный публичный ключ Telegram — лишняя
вещь, которая молча сломает вход, если его сменят.

**Заголовок JWT сверяется целиком, а не разбирается.** Классическая дыра —
поверить полю `alg` из самого токена; при сравнении целой строки ни `alg: none`,
ни смена алгоритма невозможны в принципе.

**Refresh хранится хешем и ротируется при каждом обмене.** Предъявленный дважды
означает либо кражу, либо повтор после обрыва; отличить нельзя, поэтому гасится
вся цепочка устройства. Внутри Telegram это почти бесплатно — повторный вход
молчаливый.

**Наружу уходит код ошибки, а не причина.** «Подпись не сошлась» и «срок вышел»
отвечают одинаково: различённые в ответе, они превращают его в подсказку для
подбора. Подробность остаётся в журнале Worker.

**Отчёт появился раньше данных.** Наблюдение, отложенное «на потом», не ставится
никогда, а упереться в тариф и узнать об этом от пользователей дорого.
